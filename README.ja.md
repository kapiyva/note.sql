# note.sql

パーソナルナレッジ用 SQLite フォーマットのための最小規約。

[English](README.md) | 日本語

## note.sql とは

note.sql は、SQLite をパーソナルナレッジの基盤として使うための共通規約です。

タスク、メモ、アイデア、日記。これらを束ねるデジタル手帳には、ポータブルで永続的なオープン共通規格が存在しません。既存のノートツールはアプリごとに固有のフォーマットでデータを保存しており、ここに空白があります。

note.sql は、この空白を埋めるための共通規約を定めます。ノートを表すテーブルの最小構造や命名のルールといった土台のみを規定し、具体的な表現は各フォーマット（特定のメソドロジーを表す DDL 群）に委ねます。共通の土台があることで、複数のフォーマットが同じ SQLite ファイルに共存し、ツールはフォーマットを越えて動作します。

ライブラリでも CLI でもアプリケーションでもなく、規約そのものです。誰でもこの規約に従ってフォーマットを公開したり、ツールを作ったりできます。

## なぜ SQLite か

思考の痕跡には、アプリより長い寿命が必要です。どのアプリが廃盤になっても、どのサービスが終了しても、手元に残り続けるべきものだからです。

SQL は数十年の実績を持つ、枯れたオープン規格です。書き留めた断片をビューで束ね直し、集計で傾向に気づき、検索で過去に立ち返る。手帳をめくり、思い出し、繋げ直すための語彙が、標準仕様の範囲で揃っています。

SQLite はその SQL を、単一ファイルで完結し、あらゆる環境で読み書きできる形で実装した、事実上の標準です。

同じ動機は、Markdown のようなファイル群でも一見満たせます。けれどファイルは独立した文書であり、横断して束ねる共通の手段を持ちません。タグや関係をどう表現するかはフロントマターやフォルダ構造といったゆるい慣習として個々のファイルとユーザーの規律に委ねられ、その慣習自体を配布し、別のツールで一貫して効かせる手立てもありません。note.sql ではその役割を SQLite のスキーマに担わせます。フォーマットは DDL という配布可能な成果物であり、データベースを開いた時点で構造として効き、集計や横断検索は SQL として最初から備わっています。

## 規約の概要

ノートテーブル(規約1)を1つ以上含む SQLite データベースを、note.sql のファイルと呼びます。

規約は、データの規約と公開フォーマットの規約の二つに分かれます。

データの規約は、note.sql のファイルの中にあるすべてのノートとプロパティに適用されます。

1. ノートテーブルは `id`、`title`、`body`、`created_at`、`updated_at` を持つ(規約1)
2. プロパティテーブルは `id`、`label` を持つ(規約2)
3. ノートやプロパティを指す参照には、`REFERENCES` と `ON DELETE` を書く(規約3)
4. 日時を表すカラムは `_at`、日付を表すカラムは `_date` で終わる名前にし、決まった書式で保存する(規約4)
5. ノートテーブル、プロパティテーブル、中間テーブルの、規約が定めないカラムは、nullable にするか `DEFAULT` を付ける(規約5)

作成したフォーマットは、一般に公開してかまいません。一般に公開するフォーマットは、データの規約に加えて、次の公開フォーマットの規約を満たしてください。

6. ノートテーブルを1つ以上持つ(規約6)
7. 参照先は、同じフォーマットのテーブルに限る(規約6)
8. テーブル名とビュー名に、フォーマット名のプレフィックスを付ける(規約7)

最小のフォーマットは、次の1テーブルだけで規約を満たします。

```sql
CREATE TABLE IF NOT EXISTS basic_note (
    id         TEXT PRIMARY KEY,
    title      TEXT,
    body       TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

## データの規約

### 1. ノートテーブル

note.sql の中心概念はノートテーブルです。以下のカラムを少なくともすべて持つテーブルをノートテーブルと呼びます。

```sql
id         TEXT PRIMARY KEY  -- UUID 推奨
title      TEXT              -- nullable
body       TEXT NOT NULL
created_at TEXT NOT NULL     -- UTC 日時(規約4)
updated_at TEXT NOT NULL     -- UTC 日時(規約4)
```

`body` はノートの内容そのものであり、必須です。`title` は任意の見出しです。走り書き、日記、fleeting note など、多くのノートは本文だけで成立し、見出しを付けること自体がすべてのメソドロジーにあるとは限らない編集行為だからです。

ノートテーブルをどう使うかは自由に決めてかまいません。たとえば Zettelkasten であれば、ノートテーブルを1つ持ちリンクを別テーブルで管理することも、種別（literature note / permanent note 等）ごとにノートテーブルを分けることも、どちらも規約を満たします。

### 2. プロパティテーブル

プロパティテーブルは、ノートが持ちうる値の語彙（タグ、ステータス、気分など）を表現します。以下のカラムを少なくともすべて持つテーブルをプロパティテーブルと呼びます。

```sql
id    TEXT PRIMARY KEY  -- UUID 推奨
label TEXT NOT NULL     -- 人間可読な表示値
```

`label` はその行の人間可読な表示値です。そのフォーマットを知らないツールでも、行に対して必ず表示できる唯一の文字列（タグ名、ステータス名など）を指します。

ノートからプロパティへの参照は次の2パターンです。

- 単一値 — ノートテーブルがプロパティテーブルへの参照カラムを持ちます（例: `status_id TEXT REFERENCES todo_status(id) ON DELETE SET NULL`）。ノート1件が持つ値は高々1つです。規約5により、このカラムは nullable または `DEFAULT` 付きです。
- 多値 — 中間テーブルがノートテーブルとプロパティテーブルへの参照カラムを1本ずつ持ちます（例: `todo_task_tag(task_id, tag_id)`）。ノート1件が任意個の値を持てます。

どちらのパターンでも、参照は規約3に従って宣言します。これにより、そのフォーマットを知らないツールでも、プロパティを機械的に発見できます。`id` と `label` を持つテーブルを見つけ、そこを指すと宣言された参照カラムを、ノートテーブルから直接であれ中間テーブル経由であれ、辿ればよいからです。

note.sql は主キー以外の一意性を含意しません。意味に応じて制約を張ってください。たとえば語彙に重複を許さないなら `label` に `UNIQUE` を、ノートが各タグを高々1つだけ持つなら中間テーブルに `(task_id, tag_id)` の主キーを、といった具合です。

規約1・2の形に当てはまらないテーブルは、ノートテーブルでもプロパティテーブルでもありません。note.sql は、規約3を除いて、そうしたテーブルに制限を設けません。

### 3. 参照の宣言

ノートテーブルまたはプロパティテーブルを参照するカラムは、どのテーブルにあるものでも、次の2つを宣言しなければなりません。

- `REFERENCES` による参照先
- `ON DELETE` による、参照先の行が削除されたときの意図(`CASCADE`、`SET NULL`、`SET DEFAULT`、`RESTRICT` など)

```sql
-- 中間テーブル: ノートやタグが消えたら、その結び付きも消す
task_id TEXT NOT NULL REFERENCES todo_task(id) ON DELETE CASCADE,
tag_id  TEXT NOT NULL REFERENCES todo_tag(id)  ON DELETE CASCADE,

-- 単一値: ステータスの語彙が消えたら、未設定に戻す
status_id TEXT REFERENCES todo_status(id) ON DELETE SET NULL
```

データベースを書き換える側は、宣言された意図を尊重しなければなりません。参照先の行を削除するときは、宣言どおりの結果になるようにしてください。そのための手段（データベースの外部キーの強制を使うか、自分で処理するか）は問いません。

### 4. 日時

ノートテーブル、プロパティテーブル、および規約2の中間テーブルにおいて、名前が `_at` で終わるカラムは日時を、`_date` で終わるカラムは日付を表します。日時や日付を表すカラムは、必ずこのどちらかの名前にし、次の固定長の書式で保存してください。

| 名前の末尾 | 意味 | 書式 | 例 |
|---|---|---|---|
| `_at` | UTC の日時 | `YYYY-MM-DDTHH:MM:SSZ` | `2026-11-25T10:00:00Z` |
| `_date` | 日付 | `YYYY-MM-DD` | `2026-11-25` |

桁数を固定するのは、文字列の並び順と時刻の順を一致させるためです。SQLite では、日時は `strftime('%Y-%m-%dT%H:%M:%SZ', 'now')`、日付は `date('now')` で生成できます。

ノートテーブルの `created_at` と `updated_at` もこの規約に従います。

- `created_at` は、ノートを作成した時刻です。
- `updated_at` は、ノートの内容、またはノートへのプロパティの割り当て(単一値・多値のどちらも)が最後に変わった時刻です。語彙そのもの(プロパティテーブルの `label` など)を変更しても、その語彙を持つノートの `updated_at` は変えません。

### 5. 拡張性

- ノートテーブル、プロパティテーブル、および規約2の中間テーブルにおいて、note.sql が定めるカラム以外のカラムは nullable にするか `DEFAULT` を持たせてください。これにより、note.sql が定めるカラムだけを知るツールでも有効な行を挿入できます
- note.sql が定めないことは自由に決めてかまいません

## 公開フォーマットの規約

### 6. フォーマット

フォーマットは、特定のメソドロジーを表す DDL 群です。フォーマットはデータの規約を満たし、さらに次に従います。

- ノートテーブルを1つ以上持たなければなりません。
- ノートテーブル以外のテーブル（タグ、リンク、設定など）を持ってもかまいません。複数のフォーマットが同一の SQLite データベースに共存できるため、テーブル名・ビュー名はすべて規約7のプレフィックスルールに従い、名前の衝突を防いでください。
- 参照先は、同じフォーマットのテーブルに限ります。フォーマットをまたぐ参照は、フォーマット間に依存関係を生むためです。

### 7. プレフィックスと命名

テーブル名とビュー名にはフォーマット名のプレフィックスを付けます。SQL 識別子はハイフンを使えないため、フォーマット名にハイフンが含まれる場合はプレフィックスではアンダースコアに置き換えます（例: フォーマット `cornell-notes` のプレフィックスは `cornell_notes`）。

```
<format>_<table>      -- 例: zettelkasten_note, evergreen_note
<format>_<view>_view  -- 例: zettelkasten_graph_view（ビューは推奨、必須ではない）
```

名前を揃えるため、次の作法を推奨します。

- プレフィックスより後ろの部分は単数形にします（例: `..._note`, `..._task`, `..._tag`。`..._notes` のような複数形は使いません）。
- 参照カラムの名前は、参照先テーブルの単数名からプレフィックスを除いた部分に `_id` を付けたものにします（`todo_task` → `task_id`、`todo_tag` → `tag_id`、`diary_entry` → `entry_id`）。

### 8. format.sql の再適用可能性

`format.sql` はフォーマットの完全な最新定義です。加えて、すでにデータが入っているデータベースへ再適用しても安全であること――失敗も破壊もせず、データベースを最新定義へ収束させること――を推奨します。

- テーブルとインデックスは `CREATE ... IF NOT EXISTS` を使い、既存のものに対しては再適用が no-op になるようにします
- ビューは `DROP VIEW IF EXISTS` してから `CREATE VIEW` し、常に最新定義になるようにします

ビューは状態を持たないため、`format.sql` の再適用がそのままビュー定義の更新手段になります。これによりビューの陳腐化はフォーマットの関心事から消え、マイグレーションがやるべきことは既存テーブルの変形だけになります。その変形をどう実行するかは note.sql の対象外です。

### 9. バージョン宣言

フォーマットは `<format>_meta` テーブルを持つことを推奨します。少なくとも `schema_version INTEGER NOT NULL` を持つ単一行のテーブルで、フォーマットの現在の版数を宣言します。

```sql
id             INTEGER PRIMARY KEY CHECK (id = 1)  -- 単一行
schema_version INTEGER NOT NULL
```

追加のメタデータはカラムとして持たせます（規約5に従い nullable または `DEFAULT` 付き）。単一行の強制は、上記の `CHECK (id = 1)` のような制約で表現できます。

note.sql は複数フォーマットが同一データベースに共存することを前提とするため、`PRAGMA user_version` のようなデータベース全体で1つの印は原理的に使えません。バージョンはフォーマットごとに持つしかなく、それはプレフィックス付きのテーブルを意味します（規約6・7）。そのフォーマットを知らないツールでも、このテーブルを1回引くだけでバージョンを検出できます。

後方互換性を保つ変更では `schema_version` を進めてください。既存のテーブルやカラムの削除・改名、カラムの型の変更は破壊的変更とし、別名で公開します。

## フォーマットを公開するには

1. note.sql を満たす DDL ファイル（`format.sql`）を用意します。
2. 設計意図を記述した `spec.md` を用意します。
3. 任意のリポジトリで公開します。

フォーマット名はそのままテーブルのプレフィックスになります（規約7）。同じデータベース上の他フォーマットと衝突しにくい固有な名前を選んでください。破壊的変更を別名で公開するとき（規約9）も同様です。それ以上のバージョン命名の規約を note.sql は定めません。

---

## note.sql が意図的に定めないこと

note.sql を最小限かつメソドロジー非依存に保つため、以下は規約の対象外とします。

- CRUD 操作の実装方法
- フォーマットのバージョン間のマイグレーション（定めるのはバージョンの宣言方法のみ。規約9）
- ビューの提供義務
- 特定メソドロジーの表現方法
- UI や表示に関するヒント
